## 1. 组合数：``math.comb`` vs 手写循环
   单次调用 ``C(n, 3)``（池子里取 3 件的组合数）—— 把这个微操作本身量出来。
---------------------------------------------------------------
   池子 n     math.comb      手写循环      加速比      每次省下
       10        0.1 µs        0.6 µs       4.95×        0.5 µs
       30        0.1 µs        0.6 µs       4.61×        0.5 µs
       60        0.1 µs        0.6 µs       4.49×        0.5 µs
      120        0.1 µs        0.7 µs       5.00×        0.5 µs
      300        0.2 µs        0.8 µs       4.99×        0.6 µs
---------------------------------------------------------------
   实话实说：这条改动的收益是**微秒级**的。``Σ_k C(n,k)`` 在整个项目里只被
   ``_prune_items`` 与 ``count_combos`` 各调用 ≤5 次，一次全渠道求解约 40 ms，
   所以它省下的时间占比不到万分之一 —— **不该拿它当性能论据**。
   值得做的理由是别的：不写循环、不用自己处理 k>n 与 k>n/2 的边界。
   真正把时间省下来的是第 2 节（分支定界）和第 4 节（位掩码），
   真正把内存省下来的是第 3 节（slots）。
   比值稳定在 4~5×：两个实现都是常数级操作，差距只来自
   「少三层 Python 循环」，与 n 基本无关。

## 2. 组合枚举：full（全量）vs pruned（分支定界）
   ``evaluate`` 是真实的全渠道报价，所以省下的枚举量直接换成时间。

### 样例池（10 项，真实数据），k≤5，取前 5
------------------------------------------------------------------
引擎        耗时(中位)     枚举量  下界剪枝     省下      内存峰值
full          36.07 ms        637         0     0.0%        79 KiB
pruned         9.96 ms        184       229    71.1%        25 KiB
------------------------------------------------------------------
   结果一致：是
   耗时 36.07 ms → 9.96 ms（3.62×）；枚举量 637 → 184
   下界 = (小计 × 1) − 5 分取整余量 − min(小计, 4025 分) + 0 分打包费

## 3. 对象内存：``@dataclass(slots=True)`` vs 默认（带 ``__dict__``）
   对照实现字段与 ``optimize_deals.Item`` 完全一致；样本 100,000 个对象。
-------------------------------------------------------------------------------------------------
实现                      对象本身   __dict__    合计    tracemalloc 峰值  每对象实测    实测省下
默认 dataclass                48 B      296 B   344 B           26.58 MiB     278.7 B            
@dataclass(slots=True)        80 B          —    80 B           22.76 MiB     238.7 B       14.4%
-------------------------------------------------------------------------------------------------
   两个数字都对，但含义完全不同：
   **对象 + 它自己的 __dict__** 从 344 B 降到 80 B ——
   省掉的就是后者那一整块；可字段内容（str / tuple / float）两边都要分配，
   所以摊到「每对象实测」只省 40.0 B（278.7 → 238.7 B）。
   只报前者会夸大战果，只报后者会看不出机制 —— 两个一起报。
   落在哪些类上：``Item`` / ``Coupon`` / ``Constraints`` / ``Plan`` /
   ``Channel`` / ``Quote`` / ``ChannelPlan`` / ``CouponApplication`` / ``Ledger``。
   一次全渠道求解会造出成百上千个 ``Quote`` 与 ``CouponApplication``，
   池子与叠加张数上去之后，「少一个 __dict__」就是实打实的常数额外开销。

## 4. 约束检查：位掩码随递归传递 vs 每个叶子重建 set
   掩码编译（``mask_lookup``）在计时之外 —— 对应 ``ComboIndex`` 只建一次。
--------------------------------------------------------------------------------
池子 / k              组合数        set 版        掩码版      加速比  结果一致  
22 / 2                   231      203.9 µs       65.3 µs       3.12×  是        
22 / 3                 1,540       1.82 ms      464.7 µs       3.92×  是        
22 / 4                 7,315       7.79 ms       2.40 ms       3.24×  是        
--------------------------------------------------------------------------------
   说明：``{i.code for i in combo}`` 在每个叶子都要新建一个哈希表，
   而掩码只是递归参数里的一个整数。池子越大、叶子越多，差距越明显。
